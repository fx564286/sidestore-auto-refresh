# Scarlet Crystal V118 real-device GSA initial rejection (anonymized)

Date: 2026-10-26 (KST), iOS 27.2 (24B115), embedded SideStore 3.8.9 (3.8.201).

V118 used a separate ephemeral URLSession per interactive authentication
attempt, shared through SRP init/complete and server-driven 2FA. On-device
observation:

```text
[SCARLET_V118_GSA_INTEGRITY] phase=init fields_complete=true profile_coherent=true time=within5m
[SCARLET_V98_GSA] operation=init http=200 apple_ec=-80045 anisette_family=mac sent_family=mac
[NRG_AUTH] terminal_transport_status=-80045
```

This rejects the narrow hypothesis that absent fields, obviously stale client
time, or a reused HTTP session are necessary for this specific failure. It
does **not** establish that the ADI blob was generated by a real macOS library
or that the selected Anisette server and persisted ADI were provisioned together.
The existing `profile_coherent` check compared two request-side strings
derived from the same object, not an authoritative backend fingerprint.

V119 adds read-only evidence for:
- On-device versus remote Anisette mode.
- Existing ADI blob presence (never its contents).
- Server rotation enabled or disabled.
- Selected and successful catalog *name hint*, explicitly non-authoritative.
- Configured profile family, routing override and returned header family.
- Whether fresh ADI was emitted or previous ADI used by the remote provider.

Do not log or publish Apple ID, password, token, OTP, raw ADI, server response,
UUID, DSID, or full device IDs. No new Apple request is made by the patch,
and no keychain/provisioning mutation is introduced.

Control evidence:
- SideInstaller v1.6.1 (2026-10-23) says Android-backed public anisette
  failed at GSA's later phase (-80046), and native Mac ADI plus a current
  Mac profile is now preferred.
- SideStore public reports show that GSA initial -80045 can arise before
  2FA and may persist across server/header swaps.
- URLs: https://github.com/FrizzleM/SideInstaller/releases/tag/v1.6.1
  https://github.com/SideStore/SideStore/issues/1647
  https://github.com/Dadoum/anisette-v3-server/issues/61

The application must never display a fake 2FA success or silently delete
credential or signing state to work around this error.
